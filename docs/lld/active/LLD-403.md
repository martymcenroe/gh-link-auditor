# LLD-403: candidate-analysis tool

**Issue:** #403
**Status:** Active

## 1. Problem

Deciding whether to submit a candidate means hand-stitching the DB row, the preflight report, live repo metadata, the source line in context, the maintainer's recent-PR profile, and the exact PR that would be filed. This was done ad-hoc for OasisLMF on 2026-05-26; it worked, and it should be reproducible without bespoke per-candidate agent effort. Manual stitching is the rate limit on submission throughput.

## 2. Shape

CLI subcommand (preferred over a `tools/` script, per the issue — matches `bulk-scan` / `metrics` registration):

```
ghla candidate-analysis <owner/repo> [--run-id ID] [--db PATH]
      [--format md|json] [--out PATH] [--no-live] [--reports-dir PATH]
```

Exit codes per spec: `0` success · `1` no candidate row · `2` no preflight report · `3` GitHub API failure while live.

Module split:

- `src/gh_link_auditor/candidate_analysis.py` — data assembly + both renderers
- `src/gh_link_auditor/cli/candidate_analysis_cmd.py` — arg parsing, exit codes, output routing

## 3. The mockable boundary

Per the issue: fake the *`gh` interface*, never individual httpx calls. One protocol, `GitHubFacade`, with exactly the reads this tool needs:

| Method | Backing call |
|---|---|
| `repo_metadata(owner, repo)` | `gh api repos/{o}/{r}` |
| `file_content(owner, repo, path)` | `GitHubContentsClient.fetch_file_content` |
| `path_exists(owner, repo, path)` | `gh api repos/{o}/{r}/contents/{path}` |
| `merged_prs(owner, repo, limit)` | `gh pr list --state merged --json ...` |
| `open_prs(owner, repo, limit)` | `gh pr list --state open --json ...` |

`RealGitHubFacade` implements it over `gh` (subprocess, same idiom as `repo_quality.fetch_repo_metadata`). `tests/fakes/github_facade.py::FakeGitHubFacade` is the canned-data double. Any facade call raising under live mode surfaces as exit 3; `--no-live` never constructs the facade at all.

## 4. Section assembly

`build_analysis(...) -> CandidateAnalysis` returns a dataclass with one field per spec section, so `render_markdown` and `render_json` share one source of truth (JSON is the same 12 keys — no second assembly path, which is how the two renderers stay honest).

Sourcing:

- **1 summary · 2 URLs · 5 diff** — DB row + preflight report; no live calls.
- **3 repo metadata** — facade `repo_metadata`; under `--no-live`, fields render `(unknown — needs live)`.
- **4 source context** — facade `file_content`, lines `[line-10, line+10]`, changed line marked `← THIS LINE (N)`.
- **6 gates · 7 scores** — lifted from the preflight JSON verbatim (no re-evaluation; this tool is read-only).
- **8 maintainer signals** — facade `merged_prs`/`open_prs`; style notes derived from titles (lowercase share, conventional-commits prefixes, bot-vs-human authorship).
- **9 the PR** — calls the real `pr_message.generate_pr_title_from_fixes` / `generate_pr_body_from_fixes`. Non-negotiable that these are the *actual* generators, not a copy, or the section lies.
- **10 risk** — deterministic mapping from gate results + score components + metadata (table in §5).
- **11 mechanics** — the `derive_replacement_prs.py` invocation with `--campaign-allowed`, plus the classic-PAT pinentry note and the `--dry-run` alternative.
- **12 unknowns** — static list of what was deliberately not fetched (CLA bots, PR templates, issue close-rate), plus anything skipped by `--no-live`.

### Row→fix mapping is moved, not duplicated

Section 9 needs the same row→`FixPatch`/`Verdict` mapping `tools/derive_replacement_prs.py` already has as `_row_to_fix` / `_row_to_verdict`. Copying them would create two parsers of one shape. They move into `candidate_analysis.py` as `row_to_fix` / `row_to_verdict`; the tool imports them and keeps its private names as aliases so existing call sites and tests are untouched. Direction is `tools → src`, never the reverse.

## 5. Risk mapping (deterministic)

| Risk | Source | Level |
|---|---|---|
| Dead URL still dead | gate `dead_url_still_dead` | pass → none, else high |
| Candidate URL alive | gate `candidate_url_alive` | pass → none, else high |
| Wrong target | gate `redirect_target_related` + C5 points | both good → none; C5 partial → low; else high |
| Duplicate PR | gate `no_duplicate_pr` | pass → none, else high |
| README corruption | gate `no_markdown_corruption` | pass → none, else high |
| Maintainer anti-AI | gate `anti_ai` | pass → none, else high |
| Star floor | gate `stars_floor` | pass → none, else low |
| Maintainer inactive | R2 points | full → none; partial → low; zero → high |
| Won't merge outsiders | R3 points + observed merged-PR authorship | full → none; partial → low; zero → high |

Net risk: any high → `hold`; any low → `moderate`; none → `as low as this campaign produces`.

## 6. Tests

`tests/unit/test_candidate_analysis.py` (fake facade + tmp DB + tmp report):

- all 12 sections present and ordered in markdown; JSON carries the same 12 keys
- no unrendered template markers; every URL in §2 is a markdown link or autolink
- `--no-live` performs zero facade calls and marks unknown fields
- source-context window clamps at file start/end; marks the right line
- risk mapping: all-pass → lowest net risk; a failed gate → `hold`
- §9 matches `pr_message` output byte-for-byte (guards against a divergent copy)
- exit codes 1 / 2 / 3 each triggered
- `row_to_fix` / `row_to_verdict` parity with the tool's existing expectations

`@pytest.mark.live` integration test asserts structural completeness against a real repo — opt-in, never in the default suite.

## 7. Out of scope

Per the issue: no gate/score changes (read-only), no submission, no batch mode, no TUI. **The agent never runs this against any repo** — it reads through the operator's `gh` auth; agent-driven runs would put those bytes in agent-owned process memory (ADR-0216 reasoning).
